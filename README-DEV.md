# Developing licenseproof

**Build & test:** `npm install`, then `npm run build` to compile TypeScript to `dist/`, or `npm test` to run the vitest suite directly against `src/` (no build needed for tests). `npm run dev -- scan <path>` runs the CLI without building, via `tsx`.

**Project shape:** `src/ecosystems/npm/*Parser.ts` are pure functions — `(fileContents, options) → { packages, warnings }` — with no filesystem access, which is what makes them trivial to test against fixtures. `src/ecosystems/npm.ts` is the only module that touches disk: it picks a lockfile by priority (package-lock.json > pnpm-lock.yaml > yarn.lock), calls the matching pure parser, then does the filesystem-dependent work parsers structurally can't (checking whether an optional/peer dependency is actually installed under `node_modules`, detecting monorepo workspaces, falling back when no lockfile exists).

**Adding a fixture:** create a new directory under `fixtures/`, add a `package.json` and the lockfile you're testing (plus a real `node_modules/<pkg>/package.json` if the test needs to verify on-disk presence, e.g. for optional-dependency filtering). Point a new `it(...)` block in the matching `tests/ecosystems/npm/*.test.ts` file at it by directory name — fixtures are read via `fs.readFileSync`, no registration step needed.

**Push before a session ends — always, and account for every directory a session touches, not just the ones already inside a repo you were thinking about:** work that exists only inside an ephemeral sandbox or an unpushed local folder does not exist, as far as the next session or the next agent working on this portfolio is concerned. Three real, expensive incidents now, not two. (1) ceproof's original Ed25519 signing keypair was generated inside an ephemeral build sandbox and was lost outright when that sandbox was reclaimed — recoverable only because no key had ever been sold yet, so regenerating before first sale was still possible. That was luck, not design. (2) This repo has its own version of the same mistake: the live Stripe-fulfillment Worker's entire source (`licenseproof-fulfillment`) survived for a while only as an unpushed local folder on a Mac, invisible to any other environment or session touching this portfolio, and had to be pushed to GitHub before anyone else could even see it, let alone extend it. (3) ceproof.dev's marketing site — real HTML, real SEO work, a real sitemap and analytics tag — was built and iterated on entirely inside an untracked local directory (`/home/user/ceproof-site`), with zero relationship to any git repo, until that was noticed and it was moved into `ceproof-private/site/` (matching this repo's own `site/` convention). "Push before the session ends" alone didn't catch incident 3, because that rule only fires once you're already thinking about a specific repo's uncommitted changes — a directory that was never inside any tracked repo's working tree to begin with is invisible to `git status`, `verify-pack.sh`, and every other routine check, none of which can see something that was never in their scope. Binding, in addition to pushing before the session ends: the moment a new top-level working directory is created for real, non-throwaway output, the first action taken in it — before real content accumulates — is deciding where it lives in version control and getting at least an initial commit pushed to a real remote. Not at the end; first, before there's anything real to lose. Before declaring any session's work complete, explicitly account for every directory touched or created during that session: each one resolves to either inside an already-tracked, already-pushed repo, or a deliberate, disclosed exception stated as such (a real private key file must never be git-tracked, but must still be copied to secure storage outside the sandbox — never left as the only copy anywhere, which is exactly how incident 1 happened). If a new directory's permanent home isn't obvious, stop and ask rather than letting it sit ungoverned. Push to a verified real remote before any session or work session ends, and confirm the push actually landed by running `git remote -v` again *after* pushing, not only before. Not "eventually," not "when convenient" — before the session ends.

**A guard proves nothing about a state that didn't exist when it ran — re-run `scripts/verify-pack.sh` after any change to what ships, not only when the script itself changes.** `verify-pack.sh` builds, packs, and installs a real tarball and asserts real things against it: `data/` loads from `node_modules/licenseproof/data/`, `scripts/keygen/` and all of `scripts/` are absent, no PEM private-key material or internal planning docs (milestone briefs, the internal v1 product spec, the internal binding-decisions addendum, any `*_report.md`) ship, and gating actually works against the installed CLI. A pass only proves those assertions were true against the tarball built at that exact moment — not against whatever `data/`, `scripts/`, `package.json`'s `files` array, or the packed output looks like afterward. Concretely, this repo already has a live example of how that goes stale silently: the `*_report.md` forbidden-doc check has never had anything real to catch, because this repo has never had a completion-report file — and if it ever adopts sibling repo ceproof's own naming convention for those (`M1-COMPLETION-REPORT.md` — uppercase, hyphenated, no underscore before "report"), that glob won't match it either, so the check would stay green while missing exactly the file it exists to catch. Don't trust an old `verify-pack.sh` pass once `data/`, `scripts/`, `package.json`'s `files` array, or what the tarball contains has changed since it last ran — re-run it before declaring that work done.

**Niche selection needs a written, dated kill-trigger — not a conditional held in memory.** ceproof's original kill-trigger ("reassess if a category occupant ships a sub-€300 one-time pack tier") was never written down anywhere in either repo, so per this same doctrine file's "push before a session ends" note it effectively never existed as a safeguard, and it also monitored the wrong variable (price, not category occupancy). The corrected, durable version of ceproof's reassessment gate lives in that product's own internal planning material (not in this repo, and not in ceproof's public mirror either — internal-only on both sides), reviewed on two scheduled dates. The general rule this portfolio now follows for tool #3 and beyond: niche selection ends with a written competitive map (who occupies the category, what they sell, what it costs, and whether it can be bought today — not a single conditional); every kill-trigger names a calendar date, not a milestone, because milestones get reviewed by whoever is deep in the build and dates don't; and at least one trigger must be outcome-based (no sales, no downloads) so it can fire on a failure mode nobody predicted.
